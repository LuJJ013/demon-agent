# micro-harness 项目需求

> **状态**：v0.2（2026-11-02）
> **定位**：以 Cordis 插件架构为底座，构建面向**深度网络信息爬取**与**事件逻辑归因**的 agent 系统。
> **维护方式**：先给出框架与已知需求，未决内容以 `Q-*` 编号记录，后续按讨论逐条补充。

## 1. 背景与定位

`micro-harness` 参考 [deepseek-harness](https://github.com/deepseek-ai/deepseek-harness) 的 Cordis 插件架构，目标不是只做一个能调用工具的 CLI，而是用可组合的插件搭建一条完整链路：

```text
用户需求
  → 需求理解与任务规划
  → 深度采集（站点发现、并发调度、去重、限速、重试、续跑）
  → 抽取与治理（正文、元数据、实体、事件、来源绑定）
  → 证据与知识（多源印证、冲突、时间线）
  → 归因推理（假设、证据链、置信度）
  → 交付（可复用数据资产、用户指定报表）
```

每一层通过 Cordis 服务缝与事件连接；provider 可替换，采集与推理可分开重跑。

### 1.1 场景 A：主机游戏事件溯源

输入一个模糊事件，例如“某主机游戏为何延期”“某工作室为何关闭”。

系统需要：

1. 拆解事件涉及的游戏、厂商、人物、平台与时间窗；
2. 从官网、媒体、财报、社区、招聘、专利等多类来源持续采集；
3. 抽取事件与声明，按发生时间、报道时间、更新时间建立时间线；
4. 对同一事实做多源印证，标记冲突、转载与传闻；
5. 生成候选原因、支持/反对证据、置信度与待验证缺口；
6. 输出可人工复核的溯源报告，每个结论都能回到原文片段。

### 1.2 场景 B：模糊需求 → 数据资产 / 报表

输入“近三年主机游戏的新作发布与跳票情况”这类需求。

系统需要：

1. 把模糊需求转成可执行计划：范围、实体、字段、时间窗、站点候选、产出格式；
2. 以受控并发批量采集，去重、清洗、结构化；
3. 沉淀为带 schema、版本与来源信息的数据资产；
4. 按用户指定模板生成报表，附口径说明、引用与更新时间；
5. 后续任务可复用已有资产，只补增量。

### 1.3 与现有骨架的关系

当前仓库只有包边界、服务缝、插件入口和组合配置。底座（LLM、工具、文件、网页）按第 5.1–5.5 节实现；领域能力（采集、抽取、知识、归因、报表）以新增包和插件叠加，不推翻 Cordis 架构。

## 2. 目标

| 编号 | 目标 |
| --- | --- |
| G-1 | **端到端可运行**：`mh` 能接收一次任务，完成“LLM 调用 → 工具执行 → 最终回答”的完整链路。 |
| G-2 | **可组合**：每项能力通过 Cordis 插件与服务缝提供，修改 YAML 即可装配。 |
| G-3 | **可替换**：provider 与 consumer 分离，替换 LLM、搜索、抓取或存储实现时不改调用方。 |
| G-4 | **可验证**：关键链路有离线测试；联网测试显式开启，默认不访问外网。 |
| G-5 | **最小底座**：底座不引入超出当前阶段需要的抽象、依赖和配置项。 |
| G-6 | **需求理解**：把模糊需求转成可审阅、可执行的采集与分析计划。 |
| G-7 | **深度采集**：单机高并发、持续、可恢复；按域名限速；去重；支持增量更新。 |
| G-8 | **证据化知识**：文档、实体、事件、声明与来源绑定，支持多源印证与冲突标记。 |
| G-9 | **事件归因**：构建时间线，生成可解释的归因假设与证据链，区分事实、推断、传闻与未知。 |
| G-10 | **资产与交付**：结构化沉淀为可查询、可复用、可导出的数据资产；按模板生成带引用的报表。 |

| --- | --- | --- |
| US-1 | 开发者 | 在本地运行 `mh`，让它读取文件或搜索网页后回答问题。 |

## 5. 功能需求

优先级：**P0** 首版必需，**P1** 首版后尽快，**P2** 可选。

> FR-1~FR-22 是底座能力；FR-23 起是领域能力。新增需求只追加编号，不重排已有编号。

### 5.1 LLM 与 agent 循环

| 编号 | 优先级 | 需求 | 验收要点 |
| --- | --- | --- | --- |
| FR-1 | P0 | `ctx.llm` 发送 OpenAI-compatible chat completion，支持 system/user/assistant/tool 消息与 tools schema，首版非流式。 | 用本地 stub 返回 tool call 与最终回答；请求体包含 messages 与 tools。 |
| FR-2 | P0 | `llm-deepseek` 从环境变量读取凭证，`baseURL`、`model` 可配置。 | 缺少 `DEEPSEEK_API_KEY` 时启动即报错；密钥不出现在日志中。 |
| FR-3 | P0 | `ctx.agentLoop` 循环调用模型、执行 tool calls、写回 tool result，直到无 tool call 或达到 `maxSteps`。 | 单轮与多轮 tool call 均能正确结束；超过 `maxSteps` 有明确错误。 |
| FR-4 | P0 | 工具执行失败或模型请求未知工具时，把错误写入 tool message 交回模型，不中断循环。 | 模型能收到结构化错误并给出后续回答。 |
| FR-5 | P1 | 支持流式输出与取消；收到 `SIGINT` 时中止在途请求并清理。 | 取消后进程可退出，无悬挂句柄。 |

### 5.2 会话、提示词与工具

| 编号 | 优先级 | 需求 | 验收要点 |
| --- | --- | --- | --- |
| FR-6 | P0 | `ctx.sessions` 提供内存会话，记录 user/assistant/tool 消息；模型上下文可从会话重建。 | 新增 tool result 后，下一次请求包含完整历史。 |
| FR-7 | P0 | `ctx.systemPrompt` 组装基础系统提示与已注册工具的使用说明。 | 未注册工具不出现在提示或 schema 中。 |
| FR-8 | P0 | `ctx.tools` 负责工具注册、列出与按名称执行；schema 与执行器解耦。 | 注册/卸载工具后，schema 与可执行集合同步变化。 |
| FR-9 | P0 | `ctx.agents` 提供 agent 实例工厂，`ctx.agentLoop` 与 CLI 通过它启动一次运行。 | 同一进程内可创建多个互不共享状态的 agent 实例。 |
| FR-10 | P1 | 工具调用参数校验失败时返回可读错误，不抛出未捕获异常。 | 非法 JSON 与缺参场景均有测试。 |

### 5.3 文件系统

| FR-13 | P1 | 文件大小上限可配置，超限时截断并标记。 | 大文件不会无界进入上下文。 |

### 5.5 CLI 与组合

### 5.6 需求理解与任务规划

| 编号 | 优先级 | 需求 | 验收要点 |
| --- | --- | --- | --- |
| FR-23 | P0 | 把模糊需求转成结构化任务计划：目标、实体、时间窗、站点候选、抽取字段、产出格式、预算。 | 计划可序列化、可人工审阅；缺关键信息时列出待确认项。 |
| FR-24 | P0 | 站点发现：种子 URL、搜索引擎、站点地图、链接扩展；记录每个站点的发现来源。 | 给定主题能产出候选站点列表，并说明来源。 |

| FR-26 | P1 | 计划修订：根据采集与抽取的中途结果补充或裁剪站点、字段与时间窗。 | 修订前后计划均有版本记录。 |

### 5.7 深度采集与调度

| 编号 | 优先级 | 需求 | 验收要点 |
| --- | --- | --- | --- |
| FR-27 | P0 | 持久化 frontier：URL 状态（pending/inflight/done/failed）、优先级与重试次数；重启后可续跑。 | 中断后重启不重复抓取，不丢失已完成结果。 |
| FR-28 | P0 | 并发调度：全局并发上限 + 每域名并发/速率限制；队列有界并支持背压。 | 高负载下连接数和内存有上界；单域名不会被打满。 |
| FR-29 | P0 | 去重：URL 规范化、内容哈希或 ETag；同一文档不重复处理。 | 重复链接与转载页可被识别，处理次数可统计。 |
| FR-30 | P0 | 重试与退避：对超时、5xx、限流分类重试；4xx 不重试；最大次数可配置。 | 失败分类与重试记录可查。 |
| FR-31 | P0 | 礼貌抓取：遵守 robots.txt 与站点限速，设置可识别 User-Agent；不绕过登录、付费墙或访问控制。 | 被 robots 禁止的路径不抓取；违规域名进入跳过列表。 |
| FR-32 | P1 | 增量采集：定时重访、条件请求、变更检测；只处理新增或变化内容。 | 二次运行能复用未变化文档。 |
| FR-33 | P1 | 抓取范围控制：域名白/黑名单、路径规则、深度与页数上限。 | 越界 URL 不进入 frontier。 |
| FR-34 | P2 | 分布式扩展：多 worker、多机任务分发与结果汇总。 | 首版只预留接口，不实现集群调度。 |

### 5.8 抽取、清洗与治理

| 编号 | 优先级 | 需求 | 验收要点 |
| --- | --- | --- | --- |
| FR-35 | P0 | 正文抽取：HTML → 标题、正文、发布时间、作者、语言；去除导航、广告与模板内容。 | 典型新闻页与官网公告页能抽出正文与时间。 |
| FR-36 | P0 | 结构化抽取：按任务 schema 抽取字段（游戏、平台、厂商、日期、事件类型等），保留原文片段与位置。 | 每个字段值都能定位到原文片段。 |
| FR-37 | P0 | 实体识别与归一：游戏、公司、人物、平台的别名与改名归一到同一实体。 | 同一实体不同写法合并；合并结果可追溯。 |
| FR-38 | P0 | 事件抽取：who/what/when/where + 事件类型 + 状态（传闻/官方/否认/撤回）；时间归一化到统一时区。 | 事件字段完整；不确定时间有标记。 |
| FR-39 | P0 | 来源与证据：每个断言绑定 URL、发布时间、抓取时间、原文片段与快照位置。 | 任取一条结论可回到原文并核对片段。 |
| FR-40 | P0 | 去重与聚类：同一事件的多篇报道聚类；识别转载、通稿与原始来源。 | 聚类结果保留原文集合，不丢失来源。 |
| FR-41 | P1 | 多源印证与冲突：独立来源计数、官方/一手来源权重、矛盾标记。 | 冲突内容不静默合并，单独展示。 |
| FR-42 | P1 | 质量评分：来源可信度、内容完整度、时效性；低质内容不进入结论。 | 评分维度与阈值可配置、可审计。 |

### 5.9 事件建模与归因

| 编号 | 优先级 | 需求 | 验收要点 |
| --- | --- | --- | --- |
| FR-43 | P0 | 时间线：按事件发生时间排序，区分发生、报道与更新时间；标注时间不确定性与时区。 | 时间线可导出，节点可回溯到来源。 |
| FR-44 | P0 | 归因假设：基于证据生成候选原因，每个假设列出支持/反对证据、置信度与推理链。 | 假设不是单一结论；正反证据都保留。 |
| FR-45 | P0 | 结论分级：区分事实、推断、传闻、未知；禁止把相关性直接表述为因果。 | 报告中每类结论有明确标签与依据。 |
| FR-46 | P0 | 溯源报告：事件 → 关键节点 → 证据 → 来源；支持人工复核与修订留痕。 | 复核人可逐条接受、驳回或补充证据。 |
| FR-47 | P1 | 反事实与替代解释：证据充分时给出替代原因与反证，并说明假设条件。 | 替代解释与主假设并列展示。 |
| FR-48 | P1 | 缺口识别：指出缺失证据、冲突未决点与下一步采集建议。 | 每个未决问题对应具体补充来源或字段。 |

## 7. 架构约束

| 编号 | 约束 |
| --- | --- |
| C-1 | 底座保持 5 个包：`core`、`llm-deepseek`、`fs`、`web`、`cli`；scope 为 `@micro-harness/*`。 |
| C-2 | 服务类只注册 `ctx.<key>`，不实现具体后端；provider 与 tool 插件导出 `name`、`inject`、`apply`。 |
| C-3 | consumer 只依赖服务缝（`ctx.llm`、`ctx.fs`、`ctx.web` 等），不直接依赖 provider 实现。 |
| C-4 | Cordis 使用 registry 上的 `@deepseek-ai/*` scoped 包（`~4.0.5` 系列）。 |
| C-5 | 骨架阶段源码直连：package `exports` 指向 `src/*.ts`，不生成 `lib/`。 |
| C-6 | 代码改动同步更新 README、YAML 与相关文档。 |
| C-7 | 遵循上游代码与注释风格；不为低概率风险写过度防御代码。 |
| C-8 | 底座与领域分层：领域能力新增包，不塞进 `core`；领域插件通过服务缝消费底座。 |
| C-9 | 证据优先：不存储无来源的断言；模型输出必须经过结构化校验与证据绑定。 |
| C-10 | 采集与推理解耦：采集产物先落库，抽取与归因可离线重跑、可替换模型。 |
| C-11 | 单机优先：首版单进程；分布式只预留接口，不实现集群调度。 |
| C-12 | 合规内建：robots、限速、访问控制与网络安全是必需能力，不是可选项。 |
| C-13 | 结论分级：事实、推断、传闻、未知必须显式区分；不把相关性表述为因果。 |

## 8. 里程碑

## 11. 需求维护规则

1. 新需求追加编号，不重排已有编号；删除的需求保留编号并标注“废弃”。
2. 未确认的内容写入 `Q-*`，确认后转为 `FR-*` 或 `NFR-*`。
3. 每个里程碑完成后更新第 8 节状态，并同步 README 路线图。
4. 需求变更若影响已稳定服务缝，需要同时更新 C-* 约束与相关文档。
5. 底座需求（FR-1~FR-22）与领域需求（FR-23 起）分开演进；领域需求不得破坏底座服务缝。
6. 结论性需求必须包含可验证的证据或指标，不接受“效果更好”这类不可验收的表述。
